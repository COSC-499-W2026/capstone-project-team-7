# Project Proposal for Team 7 - Web-Based Scavenger Hunt Language Game

Team Members: Gamuchirai Mhere 48169403, Madiba Burks Magara 65840381, Ashish Nayak 55942668, Dan Rukundo 57046641

## 1 Overview

### Purpose

To help beginner language learners build practical listening comprehension and vocabulary recognition skills - specifically around numbers and simple descriptive instructions in a specified language (Chinese, French, German, Japanese, Korean, or Spanish). Rather than isolating these skills in a classroom worksheet or app quiz, our system embeds them in a physical, location-based scavenger hunt across the UBCO campus, so students practice listening comprehension the way it's actually used: on the move, under mild time pressure, and tied to real-world landmarks they'll recognize again later.

### Problem Solved

Traditional classroom instruction and existing language-learning apps tend to teach numbers and directions through repetitive, static drills: flashcards, multiple choice, fill-in-the-blank, disconnected from any real environment. As a result, students often recognize numbers and vocabulary on a screen but struggle to apply that recognition in the real world, under the added cognitive load of navigating a physical space. Our web-based scavenger hunt closes that gap: students listen to an audio clip describing a location, then have to physically navigate campus and confirm they've found the right spot, turning passive listening into an active, applied skill. This also solves a secondary problem for the client (Faculty of Creative and Critical Studies) - a lack of engaging, gamified supplementary practice tools instructors can assign alongside coursework.

### Intended Users

We have three groups of intended users for the system:

- Students trying to learn a new language - Log in with personal credentials, select the language they're studying and a difficulty level (Basic, Advanced, Expert), then play scavenger-hunt sessions that test listening comprehension of numbers and location-based instructions. They accumulate points, badges, and leaderboard standing as they progress, and can review a post-session debrief highlighting what to study next.

- Teachers of the language class - Log in to a dedicated dashboard to create and manage classes, enroll students, and monitor class-wide and individual progress (points accumulated, levels completed, and leaderboard standing), giving instructors a low-effort way to track engagement outside of class time.

- System Administration - Internal accounts used by the development team for testing, account management (adding/removing student and teacher accounts), and general system maintenance, with elevated permissions beyond a standard teacher or student role.

### Special Features

Apart from the main requirements listed in the Project Details Page, our system may also offer:

- AI Chatbot: An in-app assistant students can message between sessions and interact with to further their learning through mini-quizzes and helpful tips generated by the chatbot.

- Points Redemption: students can redeem accumulated points through playing the game for in-game prizes like special profile icons, adding an incentive to continue playing the game.

- Post-hunt debrief: an automatically generated summary of what a student struggled with that session and suggests 2-3 vocab items to review, turning each session into a personalized study checklist rather than a one-off game.

- Timed runs: Students can challenge themselves by attempting to complete special hunts within the specified time limit.

### Chosen Languages: Python (Backend) and Typescript (Frontend) and FastAPI

We chose Python for the backend because our game depends on image recognition to confirm room numbers and GPS-based location matching, and Python's ecosystem (OpenCV/OCR libraries, geospatial tools like geopy) makes those features far easier to build and maintain than JavaScript's more limited options in this space. For the frontend, TypeScript pairs naturally with our React setup and adds static type checking on top of plain JavaScript; since our app is constantly passing structured data (GPS coordinates, image uploads, player/session state) between frontend and backend over the API, catching type mismatches (e.g., a coordinate sent as a string instead of a number) at compile time rather than at runtime reduces bugs and makes the codebase easier for four people to collaborate on safely.

### Chosen Framework: React.js

React with TypeScript is a good fit for our frontend because it works cleanly with our Python backend, sending and receiving data over a simple API. Best fit for GPS and photo-upload needs, keeps the frontend separate from our Python backend, and has the most support for live features like the leaderboard.

| Testing Framework | Pros | Cons |
| --- | --- | --- |
| Vitest + React Testing Library | Built to work with our React setup, no extra config needed. Tests things the way a student actually uses them (clicking "Play," uploading a photo). Shows code coverage, so we know what's tested | Not ideal for end to end testing. (We would utilize this and pytest to test both frontend and backend.) Can be difficult to test specific cases like mocking GPS and camera access |
| PyTest | Easy to integrate with CI/CD and large support online as it is commonly used. Good for testing backend logic (GPS radius checks, image recognition, points, and database access) | <br>- Only useful for our python backend <br>- Will not directly test react components <br>- Forces separation of testing frontend/backend |
| Jest | Comes with an assertion library, test runner, and mocking tools built in <br>-Snapshot testing <br>-Simple to fake API requests or databases | -Tricky ESM support <br>-Slow in large codebases <br>-Vite incompatibliity |

### Chosen Testing Framework: Vitest + React Testing Library and Pytest

Vitest works naturally with our Vite setup and tests components the way students use them. PyTest is simple and covers our backend logic well. Together they cover most of our app, but full end-to-end testing (a full game session start to finish) would need a separate tool.

### Chosen Database: PostgreSQL

We originally planned to use Firebase for authentication, paired with a SQL database for everything else. We changed this because splitting data between two systems (Firebase for accounts, PostgreSQL for everything else) adds complexity; every time we needed to connect a user to their classes or points, we'd have to join data across two separate systems. By handling authentication ourselves and keeping everything in PostgreSQL, our whole data model lives in one place, which is simpler to build, test, and query.
